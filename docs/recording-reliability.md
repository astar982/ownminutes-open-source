# 录音稳定性与识别保障

## 产品原则

OwnMinutes 的识别能力不能只依赖实时流。实时转写用于会议中辅助理解，正式纪要必须基于完整音频重新处理。

## 当前原型已加入的稳定性措施

- 使用浏览器`MediaRecorder`按1秒切分音频。
- 每个音频分片生成后立即上传到后端API。
- 后端先保存原始分片，再调用识别适配器。
- 同一会议的分片manifest写入已按会议ID串行化，避免并发上传覆盖记录。
- 自动选择浏览器支持的录音格式。
- 记录音频分片数量和缓存字节数。
- 监控麦克风输入音量。
- 监控设备中断。
- 支持选择和刷新麦克风设备。
- 使用降噪、回声消除、自动增益和单声道约束。
- 录音结束后保留可回放音频。

## 分片上传链路

```text
MediaRecorder ondataavailable
-> useStableRecorder onChunk
-> uploadAudioChunk
-> POST /api/meetings/[id]/chunks
-> saveMeetingAudioChunk
-> mockRealtimeTranscriptionAdapter
-> 返回可选逐字稿片段
```

当前原型会把分片保存到本地 `.data/meetings/{{meetingId}}/chunks/`，并维护 `manifest.json`。`.data/` 不进入Git。

## iOS 完整录音链路

```text
16kHz mono 16-bit PCM/CAF 本地中断可恢复录音
-> Expo FileHandle 每次读取 4 MiB
-> SHA-256 + 原生后台二进制上传
-> GET status 只补缺失片
-> 服务端逐片复验并顺序写入 0600 临时文件
-> ffprobe 读取文件权威时长
-> 对象存储 putFile 流式写入正式 sequence 1
-> durable receipt + 清理暂存片和临时文件
```

客户端、服务端上传提交和生产文件 ASR 都必须保持有界内存。客户端禁止恢复 `Blob`/`FormData` 整段音频上传；服务端断点续传组装禁止恢复 `Buffer.concat(buffers)`。上传提交的最大单次组装缓冲等于固定分片大小 4 MiB，正式对象通过 `meeting-object-store-contract:v3` 的 `putFile` 写入。生产对象存储模式下，会后 ASR 使用 `getFile`、文件 ffmpeg、私有临时对象和短时 SigV4 GET URL，火山请求体只含 `audio.url`，不含整段 `audio.data` Base64。只有本地存储开发模式保留 Buffer fallback，并继续受 256 MiB 上限保护。

PCM/CAF 的体积约为 32,000 B/s，90 分钟约 165 MiB，120 分钟约 220 MiB。这是为了换取 iOS 进程突然终止后仍可以确定音频布局的取舍；AAC/M4A 只在正常 `stop()` 关闭容器时可靠，不是强杀可恢复格式。

录音空间预检必须按 PCM 的实际体积预算，不能沿用 AAC/M4A 的历史阈值。当前合同为：已知剩余空间低于 512 MiB 时禁止开始，低于 1 GiB 时提示长会议风险，录音中低于 128 MiB 时只触发一次安全停止。512 MiB 启动门槛必须覆盖 120 分钟 PCM 预计最大体积 230,400,000 B 与 128 MiB 紧急余量。改变采样率、声道、位深或目标最长时长后，必须同步更新 `recording-storage.ts` 并运行 `npm run smoke:mobile-recording-storage`。

单场正式录音上限与这份预算共用同一个 120 分钟常量，并按会议会话墙钟时间计算，暂停期间也计入上限。原生 recorder 使用 `record({ forDuration })` 在后台和锁屏时独立收口，暂停后继续只传当前会话剩余秒数；原生完成事件和前台状态监听共同触发持久化兜底。完成事件状态机忽略未武装旧事件和手动停止竞态，正常到时进入 `duration-limit`，编码错误进入 `native-error`，两者都必须退出“录音中”并尝试保留文件。达到 110 分钟后 App 必须显示剩余时间和自动结束说明；达到 120 分钟时只执行一次安全停止，完整关闭录音、用本地播放器读取实际音频时长、写入本地恢复索引后才提示已保留并开始同步。播放器探测失败时回退到状态计时，上传后仍由服务端 `ffprobe` 校正权威时长。自动停止失败时不得宣称保存成功，原文件继续保留，用户可新建下一场继续录制。这样既让 iOS/Android 暂停语义一致，也避免生成超过默认 256 MiB 上传边界、只能在设备上反复失败的 PCM 文件。

## iOS 异常中断恢复

```text
App 启动读取 activeRecording 索引
-> 禁止自动上传
-> 确认文件存在且大于 1 KiB
-> 间隔 400ms 的两次大小探测一致
-> 原生播放器加载成功
-> 恢复时长至少 0.5s
-> 用户点击“检查并恢复”
-> 改为可上传索引并续传/finalize
```

任一检查失败都必须保留原文件，不得用客户端计时器伪造时长，不得把正在写入或不可读的文件发给服务端。正常录音时索引同样会是 active，因此 UI 必须同时要求 recorder 已不在 recording/paused 状态，才能展示恢复操作。

组装成功、哈希冲突、缺片、ffprobe 失败、对象存储失败都必须执行临时目录清理。正式音频写入前继续逐片核对字节数和 SHA-256；对象存储文件 PUT 预先计算完整文件哈希并签入 SigV4，同时发送精确 Content-Length。旧对象布局不变，无需迁移已有 manifest/chunks/result/Markdown。

会后识别的临时输入固定使用 `{{meetingId}}/transient/asr/{{uuid}}.ogg`：完整录音先转换为单声道语音输入、标准化到 -20 LUFS，再编码为 48 kbps OGG Opus 交给火山文件识别。默认签名有效期 1800 秒，可通过 `OWNMINUTES_ASR_AUDIO_URL_TTL_SECONDS` 在 300-3600 秒范围调整。URL 不得进入日志、诊断、纪要或验收证据；识别成功、失败、超时和重试耗尽都必须删除远程临时对象与本机 `ownminutes-asr-audio-*` 目录，生产 lifecycle 同时兜底清理 `*/transient/asr/*`。

## 识别保障策略

会议中：

- 只生成实时草稿。
- 分片推送给实时转写服务。
- 每个分片记录时间、大小、状态和重试次数。
- 如果实时转写失败，录音仍必须继续保存。

会议后：

- 使用完整音频重新转写或校正逐字稿。
- 独立执行说话人识别。
- 对逐字稿、发言人、待办、决策和总结进行结构化生成。
- 用户确认后再发布分享页和写入Obsidian。

## 说话人识别路线

### 单设备会议室录音

优点：

- 使用门槛低。
- 只需要一个人点击开始录音。

缺点：

- 多人同时说话、距离差异、噪声和混响会降低准确率。
- 实时准确区分发言人难度较高。

推荐策略：

- 实时阶段使用Speaker 1、Speaker 2占位。
- 会后做说话人识别和人工改名。
- 记录每位Speaker的声纹特征和用户改名映射。

### 多人独立音轨

优点：

- 每个参会人音轨天然对应身份。
- 发言人识别和责任归属更可靠。

缺点：

- 需要每个参会人加入会议。
- 产品复杂度更高。

推荐策略：

- 作为第二阶段团队版能力。
- 每个客户端上传独立音频流。
- 服务端按用户ID合并时间线。

## 必须避免的风险

- 不要把实时转写结果直接当正式纪要。
- 不要在单设备混合录音场景承诺100%发言人识别准确。
- 不要让实时转写失败影响原始录音保存。
- 不要默认公开逐字稿，逐字稿需要独立权限控制。
